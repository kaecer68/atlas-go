# 死碼/孤兒代碼判定機制 (Code Disposition Protocol)

> **版本**: v1.0 (2026-08-18)
> **動機**: 過去 agent 盤查常以「無消費引用」直接判死碼 → 砍掉實作未完全的孤兒代碼或重要設計。本機制強制任何「刪除/退役」決策必須通過多維度證據評估。

## 核心原則

**「沒有消費引用」是判定起點, 不是判定終點。** 一段代碼沒有被引用, 可能因為:
- A. 真死碼 (無設計意圖、無價值、有替代者)
- B. 孤兒代碼 (實作未完全, 設計意圖存在但接線未完 — 應保留/接線, 不刪)
- C. 設計儲備 (為未來功能預留, 如 PRISM Phase B/C)
- D. 已退役待清理 (功能已被替代, 但替代者已完整驗證)

## 五維度判定框架

### 維度 1: 設計意圖證據 (先查這個)
- 檔案/模組 header 註解是否說明目的?
- git log --follow 的 commit message 是否說明需求?
- 設計文件 (docs/specs, DECISIONS-LOG, AGENTS.md, architecture.md) 是否提及?
- 產品決策文件 (06-PRODUCT-DECISIONS.md, product-positioning.md) 是否規劃?
- TODO/FIXME/「待接線」標記?
- **有設計意圖 → 不是死碼**, 至少是孤兒/儲備, 進入維度 4/5 判定

### 維度 2: 業務價值 (投資人需要 / 功能缺口 / 系統穩定 / UX)
- 是否對應投資人/散戶的真實需求?
- 是否補齊某功能缺口 (即使未接線)?
- 是否對系統穩定/監控/護欄有作用?
- 是否對 UI/UX 體驗有價值?
- **四項皆無 → 才可能無業務價值**

### 維度 3: 重複/重疊/替代
- 是否有功能替代者 (且替代者更完整/已接線)?
- 是部分重疊 (如 modal 邏輯) 還是完全重疊?
- 替代者是否真的可用 (非同樣未接線)?
- **有完整替代者 → 可退役 (不是刪除, 是退役+指向替代者)**

### 維度 4: 實作狀態
- 已接線且被消費 → 活碼, 不碰
- 實作未完全 (接線中斷) → **孤兒代碼: 保留 + 標記 + 排接線 backlog**
- 已退役 (替代者完整) → 可退役清理
- 完全無痕跡 (無設計、無歷史、無價值) → 真死碼候選

### 維度 5: 影響面與風險
- 刪除後是否有隱性消費者 (dynamic import, string name, codegen, config-driven)?
- 是否被測試隱性依賴?
- 是否跨模組/跨端點共享?
- 高風險項 (核心功能/業務相關/有歷史) 需 k3 審計覆核

## 判定結論分類

| 分類 | 條件 | 處置 |
|---|---|---|
| **活碼** | 有消費引用 | 不碰 |
| **孤兒代碼** | 有設計意圖/業務價值, 但接線未完 | **保留** + 加註解標記 + 排接線 backlog |
| **設計儲備** | 明確為未來功能預留 | 保留 + 註解標記 |
| **可退役** | 有完整替代者 + 替代者已接線驗證 | 退役 (標 deprecated + 指向替代者), 可刪 |
| **真死碼** | 五維度全無證據 | 刪除 (需本機制文件佐證) |

## 執行規則 (強制)

1. **任何「刪除代碼」必須先填本機制評估表** (存 repo docs/decisions/)
2. 判定「可退役/真死碼」必須有: 設計意圖證據(無) + 業務價值(無) + 替代者(有或無) 的書面記錄
3. **孤兒代碼一律保留**, 標記 `// ORPHAN-DESIGNED: <設計意圖>` 並進接線 backlog
4. 高風險項 (業務相關/核心功能/跨模組) 需 kimi-k3 審計覆核後才能動
5. 本機制優先於任何 agent 的「無引用=死碼」直覺
