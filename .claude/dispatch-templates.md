# 派遣提示模板（含工具歷史追蹤）

## 模板結構

每次派遣 explore 代理時，提示必須包含以下結構：

```markdown
## 任務：[具體、可衡量的描述]

## 背景上下文
[簡短說明為什麼需要這個分析]

## 已執行的工具（絕對禁止重複）
- grep: "pattern" → 找到 N 個結果，主要發現：...
- read: "filepath" → 已讀取，關鍵內容：...
- ast_grep: "pattern" → 找到 N 個匹配，主要發現：...

## 已知的關鍵資訊
[從之前的工具呼叫中已經知道的資訊]

## 需要回答的具體問題
1. [問題1]
2. [問題2]
3. [問題3]

## 限制條件（強制執行）
- 最多 10 次工具呼叫
- 禁止重複相同工具+相同參數（即使認為有遺漏）
- 如果連續 3 次呼叫沒有新發現，立即停止並回報
- 優先使用 read 而非重複 grep

## 完成標準
- [ ] 所有具體問題都已回答
- [ ] 找到了關鍵檔案的路徑
- [ ] 理解了程式碼的運作方式

## 輸出格式
請提供結構化報告：
### 發現摘要
### 關鍵檔案
### 建議的下一步
```

## 使用範例

### 壞例子（會導致死循環）
```
分析 atlas-go 的市場資料系統
```

### 好例子（有工具歷史和限制）
```
## 任務：分析 atlas-go 的市場資料提供者架構

## 背景
需要理解系統如何獲取股票報價，以便評估資料品質風險。

## 已執行的工具（禁止重複）
- grep: "func.*New.*Provider" → 找到 10 個建構函式
- read: "internal/marketdata/twse.go" → 簡單的 mock 提供者
- read: "internal/marketdata/hybrid_provider.go" → 混合提供者，有 Fugle/TWSE 切換邏輯

## 已知的關鍵資訊
- TWSEProvider 回傳硬編碼的 mock 資料
- HybridProvider 會在 Fugle 失敗時切換到 TWSE
- 有 5 種不同的提供者實作

## 需要回答的具體問題
1. 生產環境使用哪個提供者？如何選擇？
2. 是否有資料品質驗證機制？
3. mock 資料是否可能意外進入生產路徑？

## 限制條件
- 最多 8 次工具呼叫
- 禁止重複 grep "func.*New.*Provider"
- 已讀取的檔案不要再讀，除非需要特定行數
- 3 次無進展則停止

## 完成標準
- [ ] 知道生產環境的提供者選擇邏輯
- [ ] 找到資料驗證程式碼（如果存在）
- [ ] 評估 mock 資料洩漏風險
```

## 工具歷史追蹤規則

### 記錄格式
```
- [工具名稱]: [精確參數] → [結果摘要（2-3句）]
```

### 必須記錄的資訊
- grep: 搜尋模式、找到幾個結果、主要發現
- read: 檔案路徑、檔案用途、關鍵內容
- ast_grep: 搜尋模式、匹配數量、主要發現
- lsp_*: 查詢的符號、找到的定義/引用位置

### 禁止的行為
- 不記錄工具歷史就派遣代理
- 記錄模糊的工具歷史（如「grep 搜尋了一些檔案」）
- 允許代理重複已記錄的工具呼叫
